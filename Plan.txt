 Saree Business Website — Final Implementation Plan                                                                                                                                                                                                                              
                                                        
 Context

 A family-owned saree sourcing and distribution business in India. Sells via WhatsApp and Facebook today. Serves boutiques, resellers, wholesalers, and retail buyers. Categories: Gadwal, Kanjivaram, Banarasi, Silk, Cotton, Linen, Organza, Handloom, and others.

 Core acquisition funnel: Instagram / Pinterest → Website → WhatsApp Inquiry → Sale

 Confirmed design: Premium / Luxury — ivory background (#FAF7F2), gold (#B8860B) + dark burgundy (#6B1E2E) accents, Playfair Display headings, Inter body. Text-based wordmark (no logo file yet).

 Build constraint: Solo developer, 4–6 week MVP, maximum business impact.

 ---
 Architectural North Star

 Do NOT build cart, checkout, or payment in MVP.

 WhatsApp is the proven conversion channel. Every page exists to drive one action: a WhatsApp inquiry or a subscriber opt-in.

 Instagram / Pinterest / Google
           ↓
     Website (catalog + collections)
           ↓
     WhatsApp CTA / Inquiry Form / Subscriber Capture
           ↓
     WhatsApp → Sale

 Database Schema

 categories (pre-seeded)

 id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
 name          text NOT NULL
 slug          text UNIQUE NOT NULL
 description   text
 image_url     text
 display_order integer DEFAULT 0

 products

 id             uuid PRIMARY KEY DEFAULT gen_random_uuid()
 name           text NOT NULL
 slug           text UNIQUE NOT NULL
 category_id    uuid REFERENCES categories(id)
 fabric_type    text
 description    text
 highlights     text[]
 base_price_min integer          -- INR; fallback when no variant price override
 base_price_max integer
 status         text NOT NULL DEFAULT 'draft'   -- 'draft' | 'published' | 'archived'
 product_code   text UNIQUE                     -- optional human-readable ref e.g. "GAD-001", "KAN-042"
 is_featured    boolean DEFAULT false
 stock_type     text DEFAULT 'supplier'          -- 'held' | 'supplier'
 created_at     timestamptz DEFAULT now()
 updated_at     timestamptz DEFAULT now()

 Status rules (product lifecycle only):
 - draft — not visible publicly; admin can edit
 - published — visible in catalog
 - archived — hidden from public; retained in DB

 ▎ Sold-out state lives at the variant level only. A published product with all variants sold out is still indexed for SEO. There is no sold_out on products — the admin marks individual color variants as sold out. The product page derives sold-out state from its variants.

 Indexes

 CREATE INDEX idx_products_status ON products(status);
 CREATE INDEX idx_products_category_id ON products(category_id);
 CREATE INDEX idx_products_featured ON products(is_featured) WHERE is_featured = true;
 CREATE INDEX idx_product_variants_product_id ON product_variants(product_id);
 CREATE INDEX idx_variant_images_variant_id ON variant_images(variant_id);

 CREATE UNIQUE INDEX idx_variant_images_one_primary
   ON variant_images(variant_id) WHERE is_primary = true;

 updated_at Trigger (applied to products and product_variants)

 CREATE OR REPLACE FUNCTION set_updated_at()
 RETURNS TRIGGER AS $$
 BEGIN NEW.updated_at = now(); RETURN NEW; END;
 $$ LANGUAGE plpgsql;

 CREATE TRIGGER trg_products_updated_at
   BEFORE UPDATE ON products
   FOR EACH ROW EXECUTE FUNCTION set_updated_at();

 CREATE TRIGGER trg_variants_updated_at
   BEFORE UPDATE ON product_variants
   FOR EACH ROW EXECUTE FUNCTION set_updated_at();

 Row Level Security

 -- Public can read published products and all supporting tables
 ALTER TABLE products ENABLE ROW LEVEL SECURITY;
 CREATE POLICY "public read published" ON products FOR SELECT USING (status = 'published');
 CREATE POLICY "admin full access" ON products USING (auth.role() = 'authenticated');

 -- Same pattern for: product_variants, variant_images, categories, collections, collection_products
 -- (public SELECT, authenticated full access)

 -- Inquiries and subscribers: public INSERT only, no public SELECT
 CREATE POLICY "public insert inquiries" ON inquiries FOR INSERT WITH CHECK (true);
 CREATE POLICY "admin read inquiries" ON inquiries FOR SELECT USING (auth.role() = 'authenticated');

 CREATE POLICY "public insert subscribers" ON whatsapp_subscribers FOR INSERT WITH CHECK (true);
 CREATE POLICY "admin read subscribers" ON whatsapp_subscribers FOR SELECT USING (auth.role() = 'authenticated');

 Caching Strategy

 Next.js 14 App Router pages are dynamic by default. Without caching, every catalog page view hits Supabase. Use ISR:

 // catalog/page.tsx, catalog/[category]/page.tsx, collections/[slug]/page.tsx
 export const revalidate = 3600  // regenerate at most once per hour

 // sarees/[slug]/page.tsx
 export const revalidate = 1800  // regenerate at most once per 30 minutes

 When admin saves a product, call revalidatePath via /api/revalidate to purge cache immediately:
 // api/revalidate/route.ts — admin-only (check auth first)
 revalidatePath('/catalog')
 revalidatePath(`/sarees/${slug}`)
 revalidatePath('/collections/[slug]', 'page')

 This means: public pages are CDN-served (fast), and changes by admin appear within seconds via on-demand revalidation.

 Security Architecture

 Admin Route Protection — middleware.ts

 // middleware.ts — runs at Vercel Edge before any /admin/* request
 import { createMiddlewareClient } from '@supabase/auth-helpers-nextjs'
 export async function middleware(req: NextRequest) {
   const res = NextResponse.next()
   const supabase = createMiddlewareClient({ req, res })
   const { data: { session } } = await supabase.auth.getSession()
   if (!session && req.nextUrl.pathname.startsWith('/admin')
       && req.nextUrl.pathname !== '/admin/login') {
     return NextResponse.redirect(new URL('/admin/login', req.url))
   }
   return res
 }
 export const config = { matcher: ['/admin/:path*'] }

 layout.tsx provides a secondary check and renders the admin shell. Both layers protect the routes.

 Cloudinary Upload — Server-Signed

 Admin image uploads never go to Cloudinary unsigned. Flow:
 1. Admin selects image in ImageUploader.tsx
 2. Client POSTs to /api/upload with auth cookie
 3. /api/upload verifies admin session → generates Cloudinary signed upload URL using CLOUDINARY_API_SECRET (server-only)
 4. Client uploads directly from browser to Cloudinary using the signed URL
 5. Cloudinary returns secure_url → stored in variant_images

 CLOUDINARY_API_SECRET never leaves the server. CLOUDINARY_API_KEY and CLOUDINARY_CLOUD_NAME are used server-side for signing only.

 Spam Protection — Inquiry Form Honeypot

 // InquiryForm.tsx — hidden field; bots fill it, humans don't
 <input
   type="text"
   name="website"
   className="hidden"
   tabIndex={-1}
   autoComplete="off"
 />
 // API route: if req.body.website is non-empty, return 200 silently (don't store)

 Simple, zero dependencies, works for the vast majority of bot spam.

 Service Role Key — Server Only

 SUPABASE_SERVICE_ROLE_KEY is only imported in:
 - lib/supabase/server.ts (used in Server Components and API routes)
 - Never in lib/supabase/client.ts
 - Never prefixed NEXT_PUBLIC_ (which would expose it to the browser)

 export function getDisplayPrice(
   product: { base_price_min: number | null; base_price_max: number | null },
   variant?: { price_min: number | null; price_max: number | null } | null
 ): PriceRange {
   if (variant?.price_min) return { min: variant.price_min, max: variant.price_max! }
   if (product.base_price_min) return { min: product.base_price_min, max: product.base_price_max! }
   return null
 }

 export function formatPrice(range: PriceRange): string {
   if (!range) return 'Price on request'
   if (range.min === range.max) return `₹${range.min.toLocaleString('en-IN')}`
   return `₹${range.min.toLocaleString('en-IN')} – ₹${range.max.toLocaleString('en-IN')}`
 }

 Lead Source Attribution

 // lib/source-tracking.ts
 const VALID_SOURCES = ['instagram','facebook','pinterest','google','direct','whatsapp'] as const
 type Source = typeof VALID_SOURCES[number] | 'unknown'

 export function captureSource(): void {
   const params = new URLSearchParams(window.location.search)
   const raw = params.get('ref') || params.get('utm_source') || ''
   const source = VALID_SOURCES.includes(raw as any) ? raw : null
   if (source) sessionStorage.setItem('lead_source', source)
 }

 export function getSource(): Source {
   const stored = sessionStorage.getItem('lead_source') as Source | null
   return stored ?? 'direct'
 }

 Validate source values against the allowlist — never store arbitrary user-supplied strings in the DB.

 Why cookie over sessionStorage: sessionStorage is cleared when the browser tab closes. A user who clicks an Instagram link today and returns to inquire 3 days later (different session) would lose attribution. A 30-day cookie correctly attributes that inquiry to
 Instagram.

 // lib/source-tracking.ts (revised — cookie-based, 30-day expiry)
 const VALID_SOURCES = ['instagram','facebook','pinterest','google','direct','whatsapp'] as const
 type Source = typeof VALID_SOURCES[number] | 'unknown'
 const COOKIE_NAME = 'lead_source'
 const EXPIRY_DAYS = 30

 export function captureSource(): void {
   const params = new URLSearchParams(window.location.search)
   const raw = params.get('ref') || params.get('utm_source') || ''
   const source = VALID_SOURCES.includes(raw as any) ? raw : null
   if (source) {
     const expires = new Date()
     expires.setDate(expires.getDate() + EXPIRY_DAYS)
     document.cookie = `${COOKIE_NAME}=${source}; expires=${expires.toUTCString()}; path=/; SameSite=Lax`
   }
 }

 export function getSource(): Source {
   const match = document.cookie.match(new RegExp(`${COOKIE_NAME}=([^;]+)`))
   const stored = match?.[1]
   return VALID_SOURCES.includes(stored as any) ? (stored as Source) : 'direct'
 }

 captureSource() is called in the public root layout.tsx via a Client Component wrapper. First-touch attribution: a cookie already set will not be overwritten (only set when a valid source param is present).

 Product Code

 products.product_code is a short, optional human-readable reference code assigned by the admin (e.g. "GAD-001", "KAN-042"). It surfaces in three places:

 1. Admin product list: code column shown alongside name for quick identification
 2. Product detail page: displayed below the product name as a small reference — Code: GAD-001
 3. WhatsApp inquiry messages: included in the pre-filled message so the seller immediately knows which item is being asked about

 The UNIQUE constraint allows NULL (multiple products can have no code), but prevents two products sharing the same code.

 WhatsApp Integration

 // lib/whatsapp.ts
 const WA_NUMBER = process.env.NEXT_PUBLIC_WHATSAPP_NUMBER!

 export function buildWhatsAppURL(opts?: {
   productName?: string
   productCode?: string
   variantColor?: string
 }): string {
   let message = "Hi, I'd like to know more about your saree collection."
   if (opts?.productName) {
     const codeRef = opts.productCode ? ` [${opts.productCode}]` : ''
     const colorRef = opts.variantColor ? ` in ${opts.variantColor}` : ''
     message = `Hi, I'm interested in the ${opts.productName}${codeRef}${colorRef}. Can you share the price and availability?`
     // e.g. "Hi, I'm interested in the Gadwal Silk [GAD-001] in Maroon. Can you share the price and availability?"
   }
   return `https://wa.me/${WA_NUMBER}?text=${encodeURIComponent(message)}`
 }

 1. Local dev: supabase start → npm run dev → all pages render, no DB errors
 2. RLS: Direct Supabase client attempt to INSERT a product without auth → rejected; INSERT an inquiry → succeeds
 3. Admin auth: curl /admin/products without cookie → 302 redirect to /admin/login
 4. Variants: Select different swatches → gallery swaps, price updates, WhatsApp message includes color name
 5. Sold-out variant: Mark one variant sold-out → swatch disabled; other variants still selectable
